# Internationalization

This is an ongoing rollout: [next-intl](https://next-intl.dev) is wired up, and the landing page, header, wallet button, theme toggle, and footer read their copy from translation files. A locale switcher in the header lets you choose a language. Other pages are being translated page by page.

## How it's wired up

- **`src/i18n/config.ts`** — the list of supported locales (`LOCALES`), the default (`DEFAULT_LOCALE`), and their display labels.
- **`src/i18n/request.ts`** — next-intl's per-request config. It reads the `NEXT_LOCALE` cookie (falling back to `DEFAULT_LOCALE`) and loads that locale's `messages/<code>.json`.
- **`next.config.ts`** — wraps the config with `createNextIntlPlugin`, pointing at `request.ts`.
- **`src/app/layout.tsx`** — resolves the locale and messages server-side (`getLocale`/`getMessages`) and wraps the app in `NextIntlClientProvider`, so both Server and Client Components can translate.
- **`messages/en.json` / `messages/es.json`** — the two locales that exist today, namespaced by component (`HomePage`, `HowItWorks`, `Header`, `Footer`, `WalletButton`, `ThemeToggle`, `LocaleSwitcher`).
- **`src/components/layout/LocaleSwitcher.tsx`** — the switcher itself, in the header. It writes the `NEXT_LOCALE` cookie and calls `router.refresh()` — there's no `[locale]` route segment, so the URL doesn't change.

## Why there's no locale-prefixed routing

next-intl's full setup adds a `[locale]` segment above every route (so URLs look like `/es/ngos/123`), plus its own routing middleware. This app already has `src/middleware.ts` doing CSP/security headers and a route-group layout (`src/app/(main)/`) added in a separate pass — layering locale-prefixed routing on top of both would touch every route, every internal `Link`, and the embed widget's URL contract (`docs/EMBED.md`), which NGOs have already pasted into their own sites. That's a real migration, not scaffolding, so it's deliberately left for whenever full i18n is actually prioritized. The cookie-based approach here gets translations, a working switcher, and the request-config plumbing in place without any of that.

**Cost of that shortcut:** `request.ts` reads a cookie to resolve the locale, and reading a cookie forces Next.js to render dynamically rather than statically — since `NextIntlClientProvider` lives in the root layout, this applies to every route, not just the translated ones. Before this change, `next build` marked `/`, `/ngos`, and the other public routes as static (`○`, with `/` and `/ngos` revalidating every 30s); after it, every route is server-rendered per request (`ƒ`). Locale-prefixed routing (the "real migration" above) would get static generation back, one prerendered page per locale — that's the other reason it's the better long-term answer, not just the URL structure.

## Adding a language

1. Add its code to `LOCALES` and a label to `LOCALE_LABELS` in `src/i18n/config.ts`.
2. Copy `messages/en.json` to `messages/<code>.json` and translate every value (keep the keys and the `HowItWorks.steps` array shape identical — `request.ts` loads whichever file matches the active locale by name, and `HowItWorks` reads `steps` as a raw array via `t.raw('steps')`).
3. That's it — the switcher reads `LOCALES` directly, so the new language appears there automatically.

## Translating another component

1. Add a namespace for it to every `messages/<code>.json` file (match the component's name, e.g. `"Footer": { "github": "GitHub" }`).
2. In a **Server Component**, call `const t = await getTranslations('Footer')` from `next-intl/server` and use `t('github')` in place of the literal string (see `src/app/(main)/page.tsx` or `src/components/landing/HowItWorks.tsx`).
3. In a **Client Component** (one with `'use client'`), use `const t = useTranslations('Footer')` from `next-intl` instead — same `t('key')` call, no `await` (see `LocaleSwitcher.tsx`).
4. A list or other non-string value (like `HowItWorks.steps`) can't go through `t()` directly — use `t.raw('key')` to get it back as plain JSON.

## Testing a component that uses translations

Rendering a component that calls `useLocale()`/`useTranslations()` outside a `NextIntlClientProvider` throws. Use the small provider wrapper from `test/renderWithLocale.tsx`, as `Header.test.tsx` does:

```ts
renderWithLocale(<Header />);
```

A Server Component using `getTranslations` (from `next-intl/server`) needs the equivalent mock for that module instead.

## Pseudo-locale (`en-XA`)

`en-XA` is a development-only pseudo-locale generated from `messages/en.json`. It makes untranslated hard-coded strings and potential layout overflow easier to identify during development.

The pseudo-locale transformation should:

- Wrap translated strings in visible markers so they are easy to distinguish from untranslated text.
- Lengthen strings to simulate the expansion that commonly occurs when text is translated into other languages.
- Preserve translation keys, interpolation variables, placeholders, and formatting tokens.
- Keep nested message structures and non-string values intact.
- Be generated from `messages/en.json` rather than maintained manually, so it stays synchronized with the source locale.

### Using the pseudo-locale

When running the application in development with `en-XA` enabled, select the pseudo-locale to inspect the UI.

Look for:

- **Untranslated strings:** text that remains in plain English without pseudo-locale markers.
- **Layout overflow:** buttons, cards, navigation, dialogs, forms, and other elements that cannot accommodate expanded text.
- **Clipping:** text cut off by fixed widths, containers, or overflow rules.
- **Wrapping issues:** labels or controls that wrap unexpectedly or disrupt alignment.

The pseudo-locale is intended for development and testing only. It must not replace English or Spanish translations or be enabled in production.
