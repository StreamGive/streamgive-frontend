# Internationalization

This is scaffolding, not a finished rollout: [next-intl](https://next-intl.dev)
is wired up, the landing page (`src/app/(main)/page.tsx` and
`src/components/landing/HowItWorks.tsx`) reads its copy from translation
files, and a locale switcher in the header lets you try it — but every other
page still has its English strings hard-coded. The goal here was to get the
plumbing in place once, so translating the rest of the app later means
extracting strings into `messages/*.json` page by page, not introducing the
library and its request-time wiring from scratch.

## How it's wired up

- **`src/i18n/config.ts`** — the list of supported locales (`LOCALES`), the
  default (`DEFAULT_LOCALE`), and their display labels.
- **`src/i18n/request.ts`** — next-intl's per-request config. It reads the
  `NEXT_LOCALE` cookie (falling back to `DEFAULT_LOCALE`) and loads that
  locale's `messages/<code>.json`.
- **`next.config.ts`** — wraps the config with `createNextIntlPlugin`,
  pointing at `request.ts`.
- **`src/app/layout.tsx`** — resolves the locale and messages server-side
  (`getLocale`/`getMessages`) and wraps the app in `NextIntlClientProvider`,
  so both Server and Client Components can translate.
- **`messages/en.json` / `messages/es.json`** — the two locales that exist
  today, namespaced by component (`HomePage`, `HowItWorks`,
  `LocaleSwitcher`).
- **`src/components/layout/LocaleSwitcher.tsx`** — the switcher itself, in
  the header. It writes the `NEXT_LOCALE` cookie and calls `router.refresh()`
  — there's no `[locale]` route segment, so the URL doesn't change.

## Why there's no locale-prefixed routing

next-intl's full setup adds a `[locale]` segment above every route (so URLs
look like `/es/ngos/123`), plus its own routing middleware. This app already
has `src/middleware.ts` doing CSP/security headers and a route-group layout
(`src/app/(main)/`) added in a separate pass — layering locale-prefixed
routing on top of both would touch every route, every internal `<Link>`, and
the embed widget's URL contract (`docs/EMBED.md`), which NGOs have already
pasted into their own sites. That's a real migration, not scaffolding, so
it's deliberately left for whenever full i18n is actually prioritized. The
cookie-based approach here gets translations, a working switcher, and the
request-config plumbing in place without any of that.

**Cost of that shortcut:** `request.ts` reads a cookie to resolve the
locale, and reading a cookie forces Next.js to render dynamically rather
than statically — since `NextIntlClientProvider` lives in the root layout,
this applies to every route, not just the translated ones. Before this
change, `next build` marked `/`, `/ngos`, and the other public routes as
static (`○`, with `/` and `/ngos` revalidating every 30s); after it, every
route is server-rendered per request (`ƒ`). Locale-prefixed routing (the
"real migration" above) would get static generation back, one prerendered
page per locale — that's the other reason it's the better long-term answer,
not just the URL structure.

## Adding a language

1. Add its code to `LOCALES` and a label to `LOCALE_LABELS` in
   `src/i18n/config.ts`.
2. Copy `messages/en.json` to `messages/<code>.json` and translate every
   value (keep the keys and the `HowItWorks.steps` array shape identical —
   `request.ts` loads whichever file matches the active locale by name, and
   `HowItWorks` reads `steps` as a raw array via `t.raw('steps')`).
3. That's it — the switcher reads `LOCALES` directly, so the new language
   appears there automatically.

## Translating another component

1. Add a namespace for it to every `messages/<code>.json` file (match the
   component's name, e.g. `"Footer": { "github": "GitHub" }`).
2. In a **Server Component**, call `const t = await getTranslations('Footer')`
   from `next-intl/server` and use `t('github')` in place of the literal
   string (see `src/app/(main)/page.tsx` or
   `src/components/landing/HowItWorks.tsx`).
3. In a **Client Component** (one with `'use client'`), use
   `const t = useTranslations('Footer')` from `next-intl` instead — same
   `t('key')` call, no `await` (see `LocaleSwitcher.tsx`).
4. A list or other non-string value (like `HowItWorks.steps`) can't go
   through `t()` directly — use `t.raw('key')` to get it back as plain JSON.

## Testing a component that uses translations

Rendering a component that calls `useLocale()`/`useTranslations()` outside
a `NextIntlClientProvider` throws. Either wrap it in one for the test, or —
the lighter option used in `Header.test.tsx` for `LocaleSwitcher` — mock
`next-intl` directly:

```ts
vi.mock('next-intl', () => ({
  useLocale: () => 'en',
  useTranslations: () => (key: string) => key,
}));
```

A Server Component using `getTranslations` (from `next-intl/server`) needs
the equivalent mock for that module instead.
